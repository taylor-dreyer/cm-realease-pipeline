## 1. Purpose and Scope
This plan defines how the myapp software product is identified, controlled,
built, released, and tracked. It applies to all source code, build scripts,
documentation, and third-party (COTS) components in this repository.

## 2. Roles
| Role | Responsibility |
|---|---|
| Developer | Implements changes on feature branches; references a ticket in every commit |
| Configuration Manager | Maintains this plan, approves merges to main, cuts releases, maintains the software library |
| Reviewer | Reviews pull requests before merge |

(For this project one person performs all roles; the process is still followed as if roles were separate.)

## 3. Configuration Identification
### 3.1 Configuration Items
- Application source (app/)
- Internal libraries (libs/libmath, libs/libutil)
- COTS components (third_party/), tracked in docs/COTS_REGISTER.md
- Build and release scripts (scripts/, Jenkinsfile, docker/)
- Documentation (docs/)

### 3.2 Version Numbering
Releases use Semantic Versioning: vMAJOR.MINOR.PATCH
- MAJOR: incompatible changes
- MINOR: backward-compatible new functionality
- PATCH: backward-compatible fixes

### 3.3 Traceability
Every build embeds the Git version, commit hash, branch, and UTC build time
(app/buildinfo.h, generated by scripts/gen_buildinfo.py). Any binary can be
traced to its exact source.

## 4. Baselines
| Baseline | Established by | Identifier |
|---|---|---|
| Development Baseline | Snapshot of develop at the end of an iteration | DB-### (annotated tag) |
| Product Baseline | Release approved and merged to main | vMAJOR.MINOR.PATCH (annotated tag) |

Baselines are annotated Git tags. Tags are never moved or deleted.
Changes to a baseline are made only through the change control process.

## 5. Branching Strategy
| Branch | Purpose | Rules |
|---|---|---|
| main | Always releasable; every commit is a product baseline candidate | Protected; changes by pull request only |
| develop | Integration of completed work | Changes by pull request |
| feature/CM-#-desc | One change per branch | Branched from develop |
| release/x.y | Release stabilization | Branched from develop, merged to main and back to develop |

## 6. Commit Standard
Format: `[CM-#] Short imperative description`
Every commit must reference a ticket so that each change traces to a request.

## 7. Change Control
